## Headline finding: Ableton Extensions SDK (public beta) — **5/ASA**

Ableton opened a **public beta** of an official, free JavaScript SDK
(`@ableton-extensions/sdk` + `extensions-cli`, packaged to `.ablx`) on **2026-06-02**
for building Extensions that run *inside* Live 12 Suite (Live 12.4.5 beta), launched
via right-click anywhere in a Set, with read/write access to tracks, clips, device
parameters, and automation. Distinct from Max for Live and Remote Scripts, and
explicitly pitched as buildable with AI coding assistance. This is the most
consequential find for ASA of any sweep to date: ASA's whole Phase-2/Phase-3 output
is "Ableton 12 device/parameter/value recommendations" delivered as text the user
applies by hand. This SDK is the first Ableton-sanctioned path to close that loop —
either a one-click-apply Extension that writes ASA's Phase-2 recommendations back
into the live set, or a read path that grounds Phase 2 in actual project state
instead of only the audio file. **Mine:** spike whether the beta's write surface
reaches device-parameter resolution (not just track/clip/automation) — that's the
granularity ASA's advice already targets; if yes, this plausibly removes the "no
action until ASA goes desktop" blocker noted in `incorporations/asa-2026-05-13.md`,
since Extensions run inside Live itself, no separate desktop shell needed.
Sources (not GitHub repos, so not added to `_seen.txt`):
[Ableton blog](https://www.ableton.com/en/blog/introducing-extensions-sdk/) ·
[public beta docs](https://ableton.github.io/extensions-sdk/) ·
[Sound on Sound coverage](https://www.soundonsound.com/news/ableton-announce-extensions-sdk).
Not yet confirmed whether ASA's own team has looked at this — worth checking before
assuming it's news to them.

Four weeks in, a hobbyist ecosystem has sprung up on this SDK (~48 repos found this
run alone). Most are one-off utility Extensions (MIDI tools, sample grabbers, chord
generators) with no DSP-analysis content — grouped under Dropped. A handful are
directly on-domain:

### [jasper-zheng/ableton-sdk-mcp](https://github.com/jasper-zheng/ableton-sdk-mcp) — **4/ASA**
MCP server letting an LLM issue Extensions-SDK commands against a running Live set
via TypeScript. First public proof that "LLM reads a JSON analysis, decides what to
change" — ASA's own Gemini-layer pattern — can be wired straight into Live instead
of stopping at advice text. **Mine:** read the tool-call surface it exposes before
building ASA's own; repo contents unread this session (GitHub access was
search-only, no `get_file_contents` outside this repo — flagged, not fabricated).

### [pnomolos/live-wire](https://github.com/pnomolos/live-wire) — **4/ASA**
"MCP bridge for Ableton Live — control Live from Claude or any MCP client via a Max
for Live proxy and the Ableton Extensions platform." A second, independent
implementation of the same MCP-over-Extensions-SDK idea as ableton-sdk-mcp, three
days apart. Two unrelated bridges appearing in the SDK's first month is a converging
pattern, not a one-off — worth tracking as a precedent for however ASA eventually
closes the advice-to-applied-change loop.

### [ImiteDev/ReverseVerb](https://github.com/ImiteDev/ReverseVerb) — **3/ASA**
"One-click reverse reverb swell for Ableton Live 12 (Extensions SDK). Offline DSP,
right-click an audio clip." Small, but a concrete end-to-end reference for "packaged
offline DSP as a Live Extension" — build, package, clip-level processing — the shape
ASA's own recommendations could ship as if the SDK spike above pans out.

### [madisonrickert/ablevsep](https://github.com/madisonrickert/ablevsep) — **3/ASA**
Extension that sends a clip to MVSEP's hosted stem-separation models and returns
stems inside Live. Conceptually overlaps ASA's own Demucs stem stage (cloud-model-in,
stems-out) and is a concrete precedent for delivering a stem result as an in-DAW
action instead of a download link.

### [borel119/Beat-Inspector](https://github.com/borel119/Beat-Inspector) — **3/tang**
"A Beat Detective–style non-warping audio quantizer for Ableton Live." Timing
correction, not analysis — adjacent rather than on-target for ASA's measurement
layer — but another concrete example of audio-domain DSP shipped as an Extension.

## Tangential but interesting

### [Mocha-Yuan/MoChord](https://github.com/Mocha-Yuan/MoChord) — **3/H**
AI-assisted guitar workspace: chord voicings, real-time tuner pitch detection, tabs,
staff notation, playback (Tauri/React, 2026-06). Guitar/tab-specific UI, not audio-
file analysis — nothing for ASA's pipeline, but a fresh real-time-pitch-detection UX
reference if Harmonia's substitutions panel ever grows a tuner/practice view.

### [jamiebullock/LibXtract](https://github.com/jamiebullock/LibXtract) — **3/ASA**
Long-standing (2012) portable C library of audio feature-extraction functions. Not
new and not actively growing, but a lighter-weight native alternative to specific
Essentia extractors if a narrow feature is ever worth decoupling from the full
Essentia dependency.

### [mir-dataset-loaders/mirdata](https://github.com/mir-dataset-loaders/mirdata) — **low/ASA**
Python loaders for standard MIR research datasets (key/chord/beat ground-truth
annotations). Not a runtime dependency, but the closest ready-made oracle set if ASA
ever wants to benchmark its chord/key/beat stages against labelled data rather than
only cross-checking against other tools (as the openmeters/soundscope loudness track
already does).
