## Track 1: openmeters → ASA loudness path

- **Source:** https://github.com/httpsworldview/openmeters — Rust,
  135★, created Oct 2025.
- **What to lift:** BS.1770-5 (2023 revision) integrated/short-term/
  momentary LUFS + true peak + spectral reassignment for the
  spectrogram path.
- **Why:** ASA's LUFS likely tracks an older BS.1770 rev; reassignment
  gives sharper time-frequency than vanilla STFT and is a visible
  quality win.
- **Approach:** port algorithms, not fork. openmeters is Rust+wgpu+Iced
  — wrong stack for Essentia.js. Lift the math and (if helpful) test
  vectors. Spectral reassignment may need a small WASM module if a
  pure-JS port is too slow.
- **Cross-check oracle:** https://github.com/bananaofhappiness/soundscope
  — Rust TUI loudness analyzer, 174★. Second BS.1770 implementation;
  use as numerical oracle, not as a dependency.
- **Definition of done:**
  - [ ] ASA's integrated loudness matches openmeters within a
        documented tolerance (e.g. ±0.1 LU) on the EBU R128 test set
  - [ ] soundscope agrees with both within the same tolerance
  - [ ] Spectral reassignment available as an opt-in spectrogram mode
        (default off until perf is characterized)
  - [ ] Test vectors + tolerance table committed to ASA
- **Risks:** spectral reassignment is non-trivial; WASM fallback may
  be needed.

## Track 2: Partiels → ASA result-interchange schema

- **Source:** https://github.com/Ircam-Partiels/Partiels — C++/JUCE,
  74★.
- **What to lift:** the *shape* of its CSV / SDIF / JSON exports — not
  code. Specifically how it tags frame-level vs per-track vs per-file
  results, and how it represents multi-channel.
- **Why:** ASA's JSON output should be a subset of what serious analysis
  tools already emit, so downstream consumers (REAPER, Max, PD) can
  adapt later with minimal glue.
- **Approach:** read Partiels' export schemas, draft an ASA JSON schema,
  freeze + version it. SDIF support is optional/secondary (binary,
  IRCAM-specific) — defer with a paragraph on when to revisit.
- **Definition of done:**
  - [ ] Partiels' CSV/JSON export schema documented in an ASA-side ADR
  - [ ] ASA's JSON output schema written down + versioned (semver on
        the schema, not the package)
  - [ ] One round-trip test: ASA JSON → CSV view comparable column-
        wise to a Partiels CSV for the same signal
  - [ ] SDIF support explicitly deferred (one-paragraph rationale)
- **Risks:** low. Pure schema work; main cost is bikeshedding.

## Track 3: forever-jukebox → ASA REST contract

- **Source:** https://github.com/creightonlinza/forever-jukebox —
  TypeScript+Python, 24★, created Jan 2026.
- **What to lift:** request/response shape, chunking, and caching
  patterns from its Essentia+madmom → JSON API. It's the closest
  public precedent for ASA's product surface (a local Spotify Audio
  Analysis replacement).
- **Why:** ASA shouldn't reinvent a contract that an existing project
  has already shipped against real consumers.
- **Approach:** read forever-jukebox's API code/docs, produce a
  side-by-side comparison with ASA's current API, classify each
  endpoint/field as adopt / adapt / reject. Don't copy wholesale —
  forever-jukebox is product-shaped (Infinite-Jukebox replacement),
  ASA is library-shaped.
- **Definition of done:**
  - [ ] Side-by-side endpoint/payload comparison committed to ASA
  - [ ] Adopt / adapt / reject list with one-line rationale each
  - [ ] ASA's API doc updated where adopt/adapt decisions land
- **Risks:** ambiguity highest of the three tracks. Easy to over-lift
  product semantics that don't fit a library. Track 2 (schema) is a
  natural prerequisite — do it first if scheduling allows.

## Out of scope (filed for later)

- Stem separation (`JeffreyCA/spleeter-web`) — revisit when ASA adds
  a stem stage.
- Fingerprinting (`JorenSix/Olaf`) — revisit if ASA needs cross-take
  alignment or in-browser identification.
- Desktop shell (`rzru/nightingale`) — template only; no action until
  ASA goes desktop. **Update (2026-07-01):** this was about ASA needing a host
  process to act on Live — the Ableton Extensions SDK now offers a real,
  official in-Live host for that, without ASA itself going desktop. See
  `asa-extensions-sdk-2026-07-01.md` for the verdict and a Part-B track;
  `rzru/nightingale` itself is still not adopted.
- Harmonia-relevant items (`ChordMiniApp`, `chordonomicon`, `rawl`) —
  separate evaluation, not ASA's problem.

## Sequencing

No required order. Recommended pickup priority by ROI:

1. **Track 2 (schema)** — cheapest, highest leverage; outputs from
   Tracks 1 and 3 ultimately serialize through this.
2. **Track 1 (LUFS)** — well-defined, testable, user-visible.
3. **Track 3 (API)** — highest ambiguity; benefits from Track 2 being
   in place.
